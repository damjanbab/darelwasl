# Skills Recap Proposal for AGENTS Integration

This file is a skills recap proposal that can be folded into AGENTS later. It reads the codebase end to end, reconstructs how the system behaves, and then derives the skills an AI agent should apply to solve problems effectively in this repository. The explanation is intentionally horizontal, meaning it stays in continuous narrative rather than a vertical checklist, so that the reader can follow the system as a flowing whole and understand how each skill connects to the next. The goal is to describe the system as it is, identify the ways a capable agent should reason about it, and then point to gaps where additional skills would materially help. The document is not a set of rules yet; it is a proposal for the skill set that fits the current codebase and its operating requirements.

The repository is a full application stack written primarily in Clojure and ClojureScript, with Datomic for persistence and a re-frame based frontend. It also includes a public site, a terminal service for Codex sessions, and a collection of registries that formalize capabilities and contracts. The structure reveals that this is not just a task app but a broader system that spans internal workflows, public content, integrations with Telegram and betting data sources, and a live terminal workflow that supports PR creation and workspace promotion. The repository is organized to reflect that scope: src contains backend and frontend code with clear namespaces such as darelwasl.http.routes for the API, darelwasl.features for the UI views, darelwasl.site for the public site, and darelwasl.terminal for the session service. Registries in registries/*.edn formalize schema, actions, views, integrations, tooling, and themes, which means changes must be synchronized across implementation and registry metadata. Scripts in scripts/ implement deployment, checks, terminal verification, and generation of docs. A sizeable docs/ section includes a system map, a generated inventory, an architecture specification for dev-local, and a pipeline spec for a Telegram first workflow that informs the client and task features. A skill set that tries to solve problems here has to understand not just Clojure syntax but the expected operational contract, the role of registries, the action gateway constraint, and the workflow enforced by terminal sessions.

The system.md document is the canonical map and it sets the tone: correctness over speed, fail closed when uncertain, and no change is valid without registry reflection. It describes registries as first class artifacts that define capabilities, and it describes the backend as the only process that can touch the main Datomic store, with external services required to use the admin action gateway. That constraint matters for any skill that touches integrations, terminal workflows, or anything in the workspace staging pipeline. The system also encodes specific content models for the control panel and the public site, including content tags, pages, blocks, and a richer v2 content model that supports a Saudi license site with business, contact, license, comparison, journey, persona, support, hero stats, FAQs, values, and team entities. This means that an AI agent must not treat content as a loose blob but as a structured schema with invariants, visibility flags, ordering, and optional section-type hints. The system demands that the public site renders from these content entities and uses tokens from the theme registry rather than hardcoded styles. Any skill that touches content or the site needs to follow those models and the theme token contract.

The backend is a Clojure service with Jetty and a modular namespace layout. The main namespace starts the service, initializes the Datomic connection, loads users, and spins up optional workers for outbox delivery, betting scheduler, and telegram polling. It also optionally starts the site server when enabled. That means an agent should be skilled in mapping config to runtime behavior, identifying which workers are enabled by environment flags, and understanding how side effect loops are controlled. It also means that system startup logic must be treated as an orchestrator and any changes in related modules are likely to have side effects on initialization, which makes testing and smoke checks crucial. There are clear boundaries for auth, schema, validation, content, tasks, users, files, clients, betting, telegram, and actions. The API routes are structured in their own namespaces, and actions are described as capability items with adapters and contracts. An AI skill in this repo must learn to navigate namespaces, know the difference between a pure core and an adapter, and follow the rule that side effects live in adapters. It also must be comfortable with Datomic patterns, including identity via UUIDs and the additional short entity ref for UI usage. It should understand that tags are entities now and that they are no longer just keyword enums, which impacts any task related to tagging or filtering.

The frontend is in ClojureScript, with re-frame for state and reagent for UI rendering. The app namespace references all feature modules and collects a large set of state defaults and helpers. It includes helper functions for building queries with pagination, parsing numeric inputs, and normalizing forms. The UI is intentionally modular, with shared components and entity rendering definitions that enforce consistency across the UI. The system expects that lists and detail views are built through shared components like entity-list and list-row, and that entity view configs live in darelwasl.ui.entity so they can be reused across features like tasks and land. This requirement yields a skill that is not just about re-frame mechanics but about the constraints of the design system, the use of theme tokens, and the requirement to render loading, empty, and error states explicitly. The UI also includes special features like the app switcher, which is expected to remain keyboard accessible and to preserve filtering state when switching. Because the site uses tokens and theme variables, a frontend skill must be able to operate within the token system and avoid hardcoded values.

The terminal service is its own subsystem, designed to manage Codex sessions, run in a separate daemon, and preserve session state across app restarts. It is a pivotal part of the system, as it is the gateway for workspace staging, command execution, and PR verification. The terminal has its own backend switching logic between stable and canary, it uses a command protocol that maps to action gateway actions, and it defines session types that enforce what operations are allowed. It stores sessions in a data/terminal structure and logs output for later review. From a skill perspective, an AI agent must understand how terminal sessions are created, how commands are claimed and executed, how workspaces are isolated by X-Workspace-Id, and how workspace promotion is the only path to move session data into main. It must also understand that terminal commands include task and file actions and that command blocks are expected to be emitted exactly. The presence of terminal-specific AGENTS templates in resources indicates that instructions differ by session type, so a skill should help the agent load the right instructions and adhere to the operational workflow.

Integrations are not incidental. The Telegram integration has a full command interface for tasks, including link token flows, pending edits, inline buttons, and notifications via an outbox. The Rezultati integration is for betting data, with constraints around polling and caching. There is also a Supersport integration path for execution, and a GitHub integration for PR handling. An agent needs to treat each integration as a contract, with explicit configuration and failure handling. It must understand that live external calls are avoided in CI and that stubs or fixtures are expected for tests. It must also account for the fact that integrations often require additional actions to be listed in the registry and often require explicit documentation in system.md. That implies a skill in integration hygiene and consistent update of registries, documentation, and adapters.

The repository reflects a disciplined approach to proofs and checks. The scripts/checks.sh harness includes targeted checks for registries, schema, actions, import, and app smoke. The smoke harness uses Playwright and includes a full build of the frontend, fixture seeding, and a login flow. The docs emphasize that changes must be validated by the proofs corresponding to touched capabilities, and that ephemeral Datomic stores are preferred in checks. There are also constraints around app port usage and a requirement that the app should refuse to start if the port is bound or the Datomic lock file is present. This implies a skill in verification planning that does not stop at running tests but maps code changes to required proofs. It also implies a skill in understanding the chain of scripts and their side effects. Because the repository can be in a dirty worktree, the skill should include a cautious approach to staging changes and handling unrelated modifications without reverting them.

The public site is not a separate repository but is a part of the same application, and it uses a design contract called site-premium-001. The requirements include a specific information architecture, a single CTA band, and a strict adherence to tokenized styling. The site renders from content entities and expects deterministic ordering and visibility handling. The site is also expected to be accessible and responsive, with specific interaction rules for the navigation and CTA. A skill for site work must therefore be fluent in the content model, the theme system, and the site server arrangement in the backend. It must also be aware of the specific section composition, which is more than a standard marketing site, because the data is loaded from Datomic and not hardcoded. This means that a site change often intersects with schema, fixtures, and content actions, which requires integrated skill across data modeling and frontend rendering.

Given this background, the skills proposed for AGENTS integration should be derived directly from the architectural contract. The first skill that emerges is registry stewardship. This skill should help an agent interpret the registry files, understand how capability IDs map to schema, actions, views, and integrations, and ensure that any change in code is mirrored in registry entries. It must also know how to update docs/system.md in lockstep with registries and how to avoid ad hoc changes that bypass the registry. This skill would include the ability to read the EDN registry format, understand required fields, and recognize when a change requires a version bump or compatibility notes. It would also guide the agent to use the registry dump endpoint when debugging, and to treat registry updates as a first class part of any relevant change.

A second skill is Datomic schema and data modeling. The codebase leans on structured entities, explicit types, and enumerated values, and it enforces invariants such as unique slugs, ordered lists, and explicit entity type assignment. A good skill in this area would help the agent choose between cardinality one or many, enforce uniqueness, add schema with proper docs, and validate invariants in the validation layer. It would also teach the agent how to update fixtures, run schema checks, and verify migrations such as entity type backfills. It would reinforce the principle that new entities must have stable ids and that relationships are modeled via refs unless the relationship has its own data, in which case a separate entity is preferred. It would also include specific behaviors like the entity ref generation and how to present refs in the UI for lookups.

A third skill is actions and adapters. The system distinguishes pure command specs from side effect wrappers, and it requires idempotency rules, audit logging, and validation before effects. Actions are registered, and their input and output contracts are part of the system mapping. A skill here would teach the agent to identify where in the code base actions are defined, to ensure action routes correspond to actions in registries, and to avoid coupling action logic directly to adapters. It would emphasize the requirement that external services go through the action gateway, and that the main app owns all Datomic writes. It would also describe how to test actions via scripts/checks.sh actions and how to design action endpoints to mirror UI payload shape, which is explicitly called out for verification. For example, creating a task should accept unnamespaced keys in the UI payload shape, and any verification should mirror that shape rather than using internal namespaces.

A fourth skill is re-frame state and UI composition. The frontend uses a shared state model with default forms and filters, and uses re-frame events to mutate state. Lists and details must be built with shared components and should not bypass the entity view configurations. A skill in this area would help the agent locate the correct feature namespace, update the relevant subscriptions and events, and keep UI state transitions consistent. It would also guide the agent to include explicit loading, empty, and error states, to use pagination controls with the required backend query parameters, and to keep list keys stable with entity ids. It should also cover the design constraints around tokenized styling, use of shared CSS classes, and accessibility requirements. This is particularly important because the system relies on a set of reusable UI primitives, and creating new components that bypass those rules would cause inconsistency and regression risk.

A fifth skill is terminal service operations. The terminal service is a separate daemon with its own API, and the system relies on it for session-based development workflows, command execution, and PR verification. A skill here would equip the agent to interpret terminal session configs, understand backend switching, manage logs, and comply with the command protocol that allows task and file actions. It would include the idea of workspace staging, where session data is created in a workspace namespace and later promoted. It would also describe the required steps for terminal verification, including creating a session, sending input, and executing at least one command. It should explicitly address how to use the session type roles and how to avoid violating constraints, such as not touching main Datomic from the session. Because the terminal service is a core feature, this skill would have to be precise and handle the interaction patterns required by the UI.

A sixth skill is integration handling, particularly for Telegram and betting sources. The Telegram integration has complex interactive flows with inline buttons and pending state. It includes link token flows, auto recognition, note creation, and pending edit sessions. A skill would need to understand the mapping between users and chats, how link tokens are generated and consumed, how to validate webhooks, and how to handle inline updates. It would also include knowledge about the outbox worker for notifications and the idempotent message keys. For the betting integration, the skill would include how to fetch reference data with caching, how to respect the no polling constraint, and how to use the scheduler in a low frequency manner. It would also include the integration with Supersport for execution. Such a skill would warn against live calls in CI and would guide the agent to use fixtures or stubs when testing.

A seventh skill is content and public site management. The system includes both control panel features and a public site with specific content models. A skill should teach the agent how content pages, tags, and blocks are modeled, how v2 entities coexist with v1 content, and how the site renderer chooses data based on section types. It should include knowledge of how the public site uses theme tokens, the exact section composition requirements, and the rule that no hardcoded tokens are allowed. It would also include how to update fixtures and content actions, how to ensure slugs and paths are unique, and how to preserve deterministic ordering for lists. Because content is likely to be edited via the control panel, this skill should align the UI flows with the schema and action contracts.

An eighth skill is checks and proof gating. The codebase has a highly structured verification matrix, and the system.md document emphasizes choosing the correct proofs based on the change. A skill here would help the agent map change types to checks, run the required scripts, and interpret logs. It would remind the agent to use temp Datomic storage for tests and to avoid contaminating local dev data. It would also include the requirement to capture browser console and network logs for UI changes, and to store those logs in the terminal log directory. This skill must emphasize that the work is not done until proofs pass and that failures should be fixed rather than reported. It would also cover how to manage app ports and avoid conflicts, since smoke tests start servers on specific ports.

A ninth skill is deployment and ops awareness. While most tasks are in development, this repo includes operational context such as the Hetzner deployment plan, systemd units, and environment variables. A skill here would be about being aware of how config toggles affect runtime behavior, how to respect ALLOW_FIXTURE_SEED, and how to interpret health endpoints. It would also cover awareness of app and site ports, the implications of enabling the site server, and the proper procedure for manual deploy or CI deploy. This skill matters because code changes can inadvertently break the assumptions of the deployment plan, and an agent needs to reason about those risks.

A tenth skill is data import and idempotency. The land registry importer is a distinct subsystem with rules about deterministic IDs and idempotent re runs. The repo includes checks that run the importer twice and compare counts, and the land API requires pagination and filter behavior. A skill in this area would help the agent understand how to normalize CSV data, how to map to entities, and how to validate that re running the importer does not create duplicates. It would also cover the query endpoints for land data and the UI constraints for presenting land people and parcels.

There are also cross cutting skills that relate to code reading and modification style. The code uses namespaces that separate core logic from HTTP routes and UI features, and it relies on a consistent pattern of configuration loading, validation, and typed entities. A general skill for this repo should include the ability to trace data flow from route to action to data to UI, with attention to the unnamespaced payloads expected by the UI and the namespaced schema attributes expected by Datomic. It should include familiarity with Clojure idioms in use here, such as maps for config, keyword based enums, and use of atoms for system state. It should also include awareness that the frontend is using JS URLSearchParams to build query strings and that the backend expects specific parameters for pagination and filtering.

The proposal also needs to identify gaps where additional skills would be helpful. One gap is observability and tracing. The system emits structured logs for HTTP handlers and workers, but there is no explicit skill to guide an agent in improving or using observability data for debugging. A skill that focuses on log strategy, log correlation for workflows, and error reporting would help maintainers diagnose issues more efficiently, especially in the terminal and Telegram flows. Another gap is performance profiling and caching. The system uses Datomic and the UI does pagination, but there is not a clear skill for assessing query performance, indexing strategy, or caching on read endpoints. A skill in performance and query optimization could help prevent regressions, especially as entities grow or the content model evolves.

Another gap is security posture and auth boundary awareness. The system uses session cookies and a simple login flow, and there is an admin action gateway that depends on a terminal admin token. However, there is no explicit skill that guides the agent through security considerations such as auth checks in routes, safe handling of tokens, and the risk of accidentally exposing admin actions. A skill here would focus on protecting the action gateway, ensuring role checks are in place, and avoiding accidental logging of secrets. It would also guide the agent in distinguishing between public site routes and authenticated app routes, and in thinking about the implications of enabling webhooks and external integrations.

A further gap is migration and compatibility management. The system is careful about schema and fixture migration, and it uses registries for compatibility flags, but there is no dedicated skill that guides the agent in how to introduce new fields while maintaining backward compatibility, or how to structure data migrations in Datomic. A migration skill would include understanding how to update fixtures safely, how to backfill new attributes, and how to run schema checks that enforce migration invariants. It would also include a methodology for deprecating fields and updating views and actions in step.

The public site design contract suggests another gap in visual design and content hierarchy. The system has strict design rules and token usage, but there is no explicit skill that helps an agent align new UI changes with the existing design language, particularly on the public site. A design system skill would encode the theme tokens, layout patterns, and accessibility rules, and would help the agent avoid creating styles that bypass the theme system. It would also guide the use of existing classes and avoid custom layout primitives where they are not necessary.

Another gap relates to workflow automation and the pipeline spec. The pipeline spec describes a Telegram first workflow that links clients and tasks and uses notes for pending reasons. There is not yet a skill that focuses on this workflow end to end, including how to build UI components and action flows that preserve minimal typing and quick button interactions. A pipeline workflow skill would help an agent implement client linking and pending flows in a consistent way, and would ensure that the UI and bot behavior align with the spec. It would also encourage tests and fixtures that capture this workflow.

A gap also exists in PR creation and verification. The repository has a terminal verification script that creates PRs, but there is no skill that guides the agent in how to use it, how to interpret the PR creation output, and how to deal with failures such as missing environment variables. A skill for PR flow would include checks, git workflow discipline, and the required steps to push branches and create PRs, along with fallback behavior when infrastructure is missing. This would be useful to reduce friction and prevent partial or stalled workflows.

Finally, there is a gap in how to manage multi service local development. The dev local universal spec makes strong statements about Datomic ownership and service topology. Yet there is no skill that teaches an agent how to start and stop services safely, handle port collisions, and avoid Datomic lock conflicts. A skill for dev local operations would cover the canonical topology, snapshot seeding, and guardrails, and would explain when to use Option A or Option B for the site and bot. This is a distinct skill from deployment because it focuses on local orchestration and the constraints of dev local Datomic.

Putting these ideas together, a proposal for AGENTS integration would include a skills file that introduces each of these skills as a named capability with an explicit description, trigger pattern, and minimal instructions. It would likely include registry stewardship, Datomic schema and modeling, action and adapter design, re-frame and UI composition, terminal service operations, integration handling, content and site management, checks and proof gating, and deployment and ops awareness. It would also include optional or gap skills like observability and tracing, performance and caching, security and auth boundaries, migration and compatibility, design system consistency, pipeline workflow automation, PR flow handling, and dev local orchestration. The file would not be a static checklist but a narrative that guides an agent to choose the right skill given the context of a task, which aligns with the current system requirement that changes be reasoned about through capability boundaries.

To ensure that this proposal is usable, it should also mention how skills interact. For example, a change to the content model would require registry stewardship, Datomic schema, content and site management, and checks and proof gating, because it affects schema, actions, views, and front end rendering. A change to Telegram commands would require integration handling, actions and adapters, and terminal service operations if the change touches session workflows. A change to the app switcher or tasks list would require re-frame UI composition and design system consistency, and it would likely trigger app smoke checks. A change to the terminal service would require terminal operations skill, dev local operations, and PR flow handling, because terminal workflows are tightly tied to session verification and action gateway usage. These cross skill interactions are part of the horizontal view of the system and should be reflected in the skills file itself, potentially through narrative examples rather than a matrix.

The proposed skills should explicitly address how the code is organized, because the system uses consistent namespaces that represent distinct domains. For instance, darelwasl.http.routes contains the HTTP routes, which are the boundary for authentication and input validation. darelwasl.actions contains action definitions that map to registry entries. darelwasl.schema defines the Datomic schema and interacts with registries to enforce invariants. darelwasl.validation implements validators for input data. darelwasl.features contains UI features that map to views. darelwasl.site and darelwasl.terminal contain their own server logic. A skill that is aligned to the system should mention these modules as navigational anchors, so that an agent can orient itself quickly and update the right files. It should also explain how the scripts directory is used to run checks, run the service, and generate docs. This is important because tasks often require running these scripts, and an agent should know how they are related to the system design.
The skill proposal should also fold in smaller but important execution habits. The system relies on fixtures for deterministic tests, expects unnamespaced UI payloads, and enforces pagination contracts, so skills should explicitly remind an agent to keep those conventions intact. The terminal command protocol, workspace promotion, log capture requirements, and the action gateway boundaries should be treated as operational invariants rather than optional niceties. The same goes for theme token usage and the use of scripts to start services or run checks. These details can be folded into the existing skills rather than repeated as separate skills, but they are not optional, and the skills file should call them out in narrative form so they are hard to miss.

The effect of this proposed skills file is to give an AI agent the same operational map that a human maintainer would have. It is not just a description of code, it is a map of how to reason about changes. It recognizes that the system is modular but also tightly governed by registry and capability contracts. It recognizes that the terminal service is an operational backbone and that the public site has strict design and data requirements. It includes the details of the integration flows, the action gateway constraints, and the proof requirements. It also recognizes where existing documentation hints at future directions, such as the pipeline spec for client workflow and the dev local universal spec, and suggests skills to make those directions easier to implement.

In terms of integration with AGENTS, the proposed skills file should likely be placed in docs and referenced from AGENTS for future sessions. The integration would include adding triggers based on tasks, such as using the registry stewardship skill when a user asks for schema changes, or using the terminal service operations skill when the task touches sessions or the command protocol. For now, this file acts as a proposal, describing the skill set, the gaps, and the rationale. It does not include enforcement rules, and it does not modify AGENTS, but it provides the content that AGENTS could point to in order to standardize agent behavior. The eventual integration would likely include referencing these skills and their trigger rules within AGENTS or within a skill registry that can be loaded by Codex.

The most important part of this proposal is that it keeps the system as a single narrative rather than a list of isolated tasks. It shows how a request about tasks might touch tags, which touches schema, which touches registries, which triggers specific checks. It shows how a request about the public site might touch content entities, fixtures, theme tokens, and UI rendering. It shows how a request about terminal workflow might touch action gateway, workspace promotion, and PR verification scripts. This horizontal view is the reason for a long form narrative, and it matches the way real tasks behave in this repository. The goal is to ensure that any agent working here can navigate the system with the same situational awareness that system.md expects.

This proposal therefore expects an AI agent to be capable of reading and using system.md and the generated system inventory, understanding the codebase structure, and choosing a set of skills that aligns with the task at hand. It expects the agent to work with a consistent approach to schemas, actions, views, and registries. It expects care with verification and a willingness to run the correct checks. It expects the agent to handle the terminal workflow, command protocol, and workspace promotion with discipline. And it expects the agent to know when a change needs to be documented and how to update the system map accordingly. It also expects the agent to recognize when a task falls into a gap area, such as performance or security, and to apply a supplemental skill to address those concerns.

To make this proposal even more actionable, the skills file should include brief descriptions of how each skill might be triggered by user requests. For example, a user request about adding a new task status should trigger the schema modeling skill, the registry stewardship skill, the actions and adapters skill, and the UI composition skill, because it would affect schema enums, registry definitions, action validation, and UI filters. A user request about adding a new public site section should trigger content model skill, schema modeling, fixtures updates, and theme usage skill, because it would touch multiple layers of data and rendering. A user request about terminal command behavior should trigger the terminal operations skill, action gateway skill, and checks skill. These examples should be expressed in narrative, not as bullet lists, to keep the horizontal style.

Finally, the proposal should include a note about how to evolve the skill set as the codebase grows. As new integrations or features are added, the skill set should be updated to include those domains. The skill file should not be static; it should evolve alongside registries and system.md. The best practice would be to update the skill file when new capabilities are added, so that the next agent has a clear map of the system and the required practices. In this way, the skill file becomes a living companion to system.md, capturing not just what the system is, but how to work on it effectively.

By creating this long form skill recap, the system gains a narrative map that complements its formal registries. It makes the hidden assumptions explicit, emphasizes the cross cutting workflows, and surfaces areas where additional skill guidance would help. It is a proposal, not a rule, but it is designed to be immediately useful and easy to integrate into AGENTS when the time is right.
